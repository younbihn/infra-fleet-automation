## 2. Shell 스크립트 (evolution/01-shell) — 2026-09-09

**실행**: `./bootstrap.sh 192.168.64.3 minkyluv`

| 항목 | 값 |
|---|---|
| 대상 서버 | 1대 (순차) |
| SSH 연결 | 5회 (단계마다 연결·종료 반복) |
| 인증 입력 | **10회** (SSH 5 + sudo 5) |
| 재실행 시 | 변경 여부와 무관하게 전 작업 재수행 |

**관찰된 한계**
- 사람이 인증을 10회 입력해야 하므로 **무인 실행 불가** = 진정한 자동화가 아님
- 서버 10대로 확장 시 인증 입력 100회 → 실용성 없음
- `useradd`는 계정이 있으면 에러 → `|| echo '이미 존재'` 예외 처리를 직접 코딩
- `tee`로 authorized_keys를 **덮어씀** → 기존 키가 있었다면 유실 (실무였다면 사고)
- firewalld: 상태 확인 없이 무조건 실행 → `ALREADY_ENABLED` 경고
- sudoers 문법 검사가 배포 **이후**에 이루어짐 → 잘못된 파일이 이미 적용됨

## 3. Ansible (playbooks/bootstrap.yml) — 2026-09-09

**실행**: `ansible-playbook -i inventory/hosts.yml playbooks/bootstrap.yml -K`

| 항목 | 값 |
|---|---|
| 대상 서버 | **2대 병렬** (lab01, lab02) |
| 소요 시간 | **8.5초** |
| 인증 입력 | **1회** (-K로 입력 후 전 호스트·전 태스크에 재사용) |
| 태스크 수 | 8개 |

**멱등성 검증**

| 실행 회차 | lab01 | lab02 |
|---|---|---|
| 1회차 | ok=8, changed=1 | ok=8, changed=0 |
| 2회차 | ok=8, **changed=0** | ok=8, **changed=0** |

→ 2회차 전 태스크 `ok`, `changed=0`. 멱등성 확보.

**부수 효과 — 설정 편차 자동 수렴**
1회차에서 lab01의 sudoers 태스크만 `changed`로 보고됨. lab01에는 해당 설정이
누락돼 있었고 Ansible이 이를 감지·적용. 서버 간 설정 편차가 자동으로 수렴됨을 확인.

| 항목 | 수동 | Shell | Ansible |

## 7. 장기 방치 후 멱등성 재검증 (2026-10-26)

최초 구성(2026-09-09)으로부터 **47일 경과** 후 동일 플레이북을 재실행.
그 기간 동안 VM 2대는 일시정지 상태로 방치됨.

| 호스트 | ok | changed | failed |
|---|---|---|---|
| lab01 | 8 | **0** | 0 |
| lab02 | 8 | **0** | 0 |

→ 8개 태스크 전부 `ok`. 선언한 상태가 47일간 유지됨을 확인.

**부수 발견: 시간 동기화의 함정**

재개 직후 lab02의 시각이 정지 시점(09-09 14:27)에 멈춰 있었음.
그런데 `timedatectl` 은 `System clock synchronized: yes` 를 보고.

- 해당 플래그는 chrony가 과거에 소스와 맞춘 적이 있다는 상태값이며,
  현재 시각의 정확성을 보장하지 않는다
- chrony의 기본 보정 방식은 slew(미세 조정)이므로 47일 규모의 오차는 메울 수 없다
- 플레이북의 `chronyc makestep` + `hwclock --systohc` 태스크가 이를 복구

→ 교훈: 서비스가 active인 것, 플래그가 yes인 것, 실제로 정확한 것은 각각 다르다.
   점검은 상태 플래그가 아니라 실측값(date)으로 해야 한다.

**점검 스크립트 개선 (scripts/checkup.sh)**

초기 버전은 조치(플레이북 실행) 이후 재확인 단계가 없어, 로그에 보정 전 상태만
남고 복구 여부를 판단할 수 없었다. 조치 후 재확인 섹션을 추가하여 해결.
→ 운영 점검은 "조치"가 아니라 "조치 후 검증"까지가 한 단위.

## 10. 로드밸런서 경유 지연 (2026-11-14)

**환경**: 맥(M1)과 VM(Rocky 9, UTM 공유 네트워크)이 같은 호스트 안, HAProxy 2.8.14 roundrobin, `scripts/netprobe.py`, HTTP `/health`, 평상시 상태(장애 주입 없음), 요청마다 새 연결, 각 20회 중앙값(각 한 번 실행, 직접 접속을 먼저 측정)

| 경로 | tcp(ms) | 첫바이트(ms) | 전체(ms) |
|---|---|---|---|
| 맥 → lab01 직접 | 0.83 | 0.45 | 1.28 |
| 맥 → lb01 → lab01/02 | 0.68 | 1.14 | 1.83 |
| 차이 (LB 경유 - 직접) | -0.15 | +0.69 | +0.55 |

**관찰**:
- LB를 거치면 전체 중앙값이 약 0.55 ms 늘었다. 늘어난 몫은 거의 전부 첫바이트(+0.69 ms)로, HAProxy가 요청을 읽고 백엔드에 다시 접속해 응답을 돌려주는 시간으로 보인다(HAProxy 내부 처리 시간은 따로 재지 않았다).
- tcp 단계는 LB 경유가 0.15 ms 더 짧게 나왔다. 표본이 작고 측정 순서의 영향일 수 있어 의미 있는 차이로 보지 않는다.
- 첫 시도가 느리다(직접 7.23 ms, LB 경유 10.41 ms). 평균(1.67 ms, 2.50 ms)이 중앙값보다 큰 이유이며, 중앙값을 대표값으로 쓴다.
- LB 경유 20회의 응답은 lab01 10회, lab02 10회로 번갈아 나와 roundrobin이 보인다. 성공은 둘 다 20회, 실패 0건.

**한계**: 같은 호스트 안의 가상 네트워크라 실제 망 지연이 없음. 표본 20회를 각 한 번만 측정했고 순서를 바꾸거나 반복하지 않아 0.55 ms 차이가 측정 잡음과 구분되는지는 확인하지 못함. 부하가 있을 때의 지연은 이 값으로 말할 수 없음.
